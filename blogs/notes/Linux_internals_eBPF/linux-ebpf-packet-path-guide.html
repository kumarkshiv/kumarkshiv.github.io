The one analogy to keep in your head all the way through

The kernel is an airport. Bags (packets) come off the plane onto a conveyor that drops them straight into bins (DMA into the ring buffer) — no staff member carries each bag. A worker comes by and collects a batch of bags at a time (NAPI) instead of being phoned for every single one. At the very first gate stands a sniffer dog (XDP): it can throw a bag away before anyone spends money on it. Past the dog, every bag gets an expensive printed tag with its details (the sk_buff). Then comes customs, which can read the tag (TC), passport control that keeps a record of every traveller (Netfilter + conntrack), a signboard that says "this terminal or connecting flight" (FIB routing lookup), and finally baggage claim (the socket), where the passenger picks the bag up (recvmsg()). The further a bag travels before you reject it, the more you have already paid for it.

01

The big picture: a packet's journey through the kernel

Why it's examinableHook placement is the first question in any packet-processing design review: the answer decides your cost per packet before you write a line of code. Interviewer asks"Walk me through what happens when a packet arrives at a Linux server. Why is XDP faster than iptables/nftables?"

1.1Mental model first

The receive path is an assembly line. Each station knows more about the packet and costs more CPU time than the one before it. So the speed of a tool (XDP, TC, nftables) is decided mostly by which station it stands at, not by how clever its code is. XDP is fast because it runs before the kernel spends money on the packet.

Key concept

Every arrow in the diagram has a cost, and costs add up. The earlier you make a decision (drop, redirect), the fewer stages you pay for. That is the whole reason XDP exists.

Trap

"XDP is fast because eBPF is fast." No — nftables and TC can also be very efficient. XDP is fast because of where it runs: before sk_buff allocation, before GRO, before conntrack, before rule chains.

Common mistake

Expecting tcpdump to show packets your XDP program dropped. Packet taps (AF_PACKET) hook in after the SKB exists, so an XDP_DROPped frame is invisible to tcpdump, conntrack and every counter above the driver. Count drops in a map instead.

02

Step 1 — the NIC, DMA and the ring buffer

Why it's examinableEvery later cost model (NAPI, XDP, AF_XDP zero-copy) assumes you understand who owns which buffer and when. Interviewer asks"Why doesn't a NIC interrupt the CPU for every packet? What is a ring buffer and what happens when it fills up?"

2.1Why one interrupt per packet is a disaster

At 10 Gbps with 1500-byte frames, the wire can carry about 10,000,000,000 ÷ (1500 × 8) ≈ 833,000 packets per second. Every interrupt forces the CPU to stop, save state, jump into a handler and return — and it disturbs the CPU cache. At that rate the CPU would spend almost all its time entering and leaving interrupt handlers and almost none doing useful work. This failure has a name: receive livelock.

2.2DMA: the card writes into RAM by itself

  1. At driver init, the kernel pre-allocates packet buffers and a descriptor ring, and tells the NIC the ring's (IOMMU/physical) address.
  2. A frame arrives. The NIC copies its bytes into the next free buffer using DMA — the CPU is not involved in the copy.
  3. The NIC writes length + status into that descriptor and advances its head index.
  4. The NIC raises an interrupt — once per batch, not once per packet — saying "I've got packets, come look".
  5. Later the driver walks from its tail index, consumes filled descriptors, and refills those slots with fresh buffers.

Ring buffer simulator (8 slots)

The NIC writes at the head, the driver reads from the tail. Fill it faster than you drain it and watch drops appear — this is what rx_missed-style counters report.

Key concept
The ring is per queue. A multi-queue NIC (lesson 4) has one RX ring, one TX ring and one interrupt vector per queue.

  
Common mistake
"Just make the ring bigger and drops go away." A bigger ring absorbs short bursts, but it adds latency (packets wait longer) and uses more memory and cache. If the CPU can't keep up on average, a bigger ring only delays the drops.

    2.

    3.

    5.

04
Multi-queue NICs, RSS and IRQ affinity

  

    Why it's examinableExplains why adding cores often doesn't raise receive throughput, and decides which CPU your XDP program runs on.
    Interviewer asks"Our 32-core box drops packets while 31 cores are idle. What would you check?"
  


  
4.1Why one queue is not enough

  
A single-queue NIC raises one interrupt and delivers all traffic to one CPU. At low rates nobody notices. At high rates that one CPU hits 100% in IRQ/NAPI, its ring fills, packets drop — and the other cores sit idle. More application threads can't help: the serialization point is the hardware queue, below the layer most engineers look at.


  
4.2What a "queue pair" is

  
    
    
  • RX ring — descriptors pointing at memory the NIC fills via DMA.
    • 
    
  • TX ring — descriptors pointing at memory the CPU fills for transmission.
    • 
    
  • Its own MSI-X interrupt vector — one IRQ per queue, not one for all traffic.
    • 
    
  • Its own NAPI instance — so CPU 0 drains queue 0 while CPU 1 drains queue 1, with no locking between them.
    • 
  


  
4.3RSS — Receive Side Scaling

  
RSS is a hardware feature: the NIC hashes each packet's 5-tuple (typically a Toeplitz hash with a configurable secret key), uses the hash to index an indirection table (RETA), and the table entry names the queue. Same 5-tuple → same hash → same queue → same CPU, so a TCP flow's packets are processed in order.

Common mistake — the part people get wrong
Configuring 16 queues but leaving all 16 IRQs on CPU 0. You get multi-queue hardware with single-core throughput. Always check /proc/irq/N/smp_affinity_list. For latency-sensitive boxes, pin manually rather than letting irqbalance move IRQs at awkward moments.

  
Trap — RSS spreads flows, not packets
One exact 5-tuple always lands on one queue, so a single huge "elephant" flow still saturates one core. A flood from one source IP but many source ports (or spoofed tuples) does spread across queues — which is why the maps lesson worries about several CPUs updating the same per-IP counter.

  
Precision note — symmetric keys
The notes flag a symmetric RSS key (forward and reverse direction of a connection hash the same) as a common misconfiguration for general servers. Some middleboxes and IDS tools want exactly that so both directions land on one core. Know which one you need and verify with ethtool -x.

RPS and RFS — steering in software

  

    Why it's examinableVMs and cheap NICs are single-queue; knowing the software fallbacks and their cache costs is standard systems-performance material.
    Interviewer asks"Your VM has one RX queue and one hot core. How do you spread the work, and what does RFS add on top?"
  


  
5.1RPS — Receive Packet Steering

  
RPS is software RSS. The single queue is still drained by one CPU, but after the SKB is built the kernel computes the flow hash in software and queues the packet onto another CPU's backlog, waking that CPU with an inter-processor interrupt (IPI). That CPU finishes the stack work in its own softirq.

  
5.2RFS — Receive Flow Steering

  
Problem: RPS sends a flow to CPU 3, but the application thread reading that socket runs on CPU 5. Every packet crosses CPUs and arrives in a cold cache. RFS fixes it: when an app calls recvmsg() on CPU 5, the kernel records flow_hash → CPU 5 in a flow table, and RPS then steers that flow's future packets to CPU 5. Packet processing, socket state and the app all share one warm L1/L2 cache.

Key concept — ordering
RSS (hardware) → NAPI → XDP → build_skb() → RPS/RFS → TC → Netfilter → socket. An XDP_DROP never reaches RPS/RFS, so flood traffic never touches the RFS flow table.

  
Trap
RFS adds a hash-table lookup per packet. At flood scale that table thrashes. For DDoS mitigation RFS is irrelevant — drop in XDP first; legitimate traffic that is XDP_PASSed then benefits from RFS locality.

  
Common mistake
Setting rps_flow_cnt per queue larger than rps_sock_flow_entries ÷ number_of_queues, or configuring RFS without enabling RPS first. RFS only overrides RPS's choice; with RPS off there is nothing to override. Treat RPS as damage control on limited hardware, not an architecture.

  
Beyond the notes
Accelerated RFS (aRFS) pushes the RFS decision into NIC hardware filters (needs ntuple filter support in the driver), so the right queue — and CPU — is chosen before the interrupt fires.

GRO, GSO, TSO, LRO — how the kernel "cheats"

  

    Why it's examinableOffloads change what every layer sees — packet counts, invocation counts, checksum validity — and XDP sits on the "wrong" side of GRO on purpose.
    Interviewer asks"What's the difference between GSO and TSO, and GRO and LRO? Does XDP see GRO-merged packets?"
  


  
6.1The one idea behind all four

  
Key concept
Per-packet overhead is the bottleneck, not per-byte overhead. Allocating an sk_buff, parsing headers, a conntrack lookup, a routing decision, waking a socket — each is paid once per packet. Make each "packet" carry more bytes and you pay those costs fewer times. The wire still carries 1500-byte frames; offloads only change when and where segmentation or merging happens.

6.2TSO — TCP Segmentation Offload (transmit, hardware)

  
Your app calls write(fd, buf, 64000). Without TSO, tcp_write_xmit() cuts about 43 MSS-sized segments (MSS ≈ 1460 bytes on IPv4 with a 1500 MTU), wraps each in TCP and IP headers and pushes each one to the driver: 43 operations for one write. With TSO, the kernel builds headers once and hands the NIC one large buffer tagged with gso_size = 1460; the NIC slices it in silicon, stamping sequence numbers, IP lengths and checksums on each frame.


  
6.3GSO — Generic Segmentation Offload (transmit, software)

  
GSO is the software fallback for NICs without TSO, and for protocols TSO doesn't cover (UDP, tunnels such as GRE/VXLAN). The kernel keeps the data as one super-SKB through TC, Netfilter and routing — those layers pay their cost once — and segments it at the last possible moment, just before the driver's ndo_start_xmit.


  
6.4GRO — Generic Receive Offload (receive, software)

  
GRO runs in the NAPI poll loop and merges frames of the same flow into one large SKB before the stack sees them. It only merges when the 5-tuple matches, sequence numbers are contiguous, and flags are compatible — never out-of-order segments or different flows. Result: one conntrack lookup, one TC run, one Netfilter pass and one socket wake-up instead of 43.


  
6.5LRO — Large Receive Offload (receive, hardware)

  
LRO merges TCP segments inside the NIC, before the kernel ever sees the individual frames. For one isolated stream on a pure endpoint it can be marginally faster (one DMA write instead of 43). But the hardware doesn't understand routing tables, TTLs or kernel state, so per-frame information (TTL, IP ID, some flags) is lost. Forwarding decisions would be made on a merged frame. That's why LRO is off by default and GRO is used instead.

6.6Why XDP developers must care

  
    
    
  1. XDP runs before GRO, so it sees wire frames. A 10 Gbps bulk TCP flow is ~43× more XDP invocations than the application byte rate suggests — roughly 800k map lookups per second for that one connection. Fine for IP/port filtering (every frame has full headers); the wrong hook for inspecting whole application messages.
    2. 
    
  2. XDP_TX and XDP_REDIRECT bypass TSO. You transmit individual raw frames; the NIC's TSO engine runs only on the normal TX path.
    3. 
    
  3. Rewrite a byte → fix the checksum yourself. RX checksum offload validated the original bytes. Nothing recomputes it on XDP_TX/XDP_REDIRECT, so a rewrite without a checksum update produces corrupt traffic.
    4. 
  

  
The incremental update rule (RFC 1624) — change field m to m' and the checksum HC becomes: HC' = ~(~HC + ~m + m') in one's-complement arithmetic. No need to re-sum the whole header.

  

  

  
Precision note
bpf_l3_csum_replace() and bpf_l4_csum_replace() take an sk_buff, so they are available to TC programs, not XDP. In XDP you use bpf_csum_diff() plus a fold, or write the RFC 1624 update inline.


  
6.7Check the settings

  


  
Trap — your counters lie (politely)
An nftables packet counter on a bulk flow counts GSO/GRO super-packets, not wire frames: one "packet" may be 43 frames. Per-packet rate limits and accounting rules must take that into account.

  
Common mistake
Turning LRO on for "more throughput" on a router or an XDP forwarder. It merges frames the forwarding path must see individually. Keep it off unless the box is a pure endpoint and you've measured.

  
Beyond the notes
UDP didn't lose segmentation when UFO went away: UDP GSO (the UDP_SEGMENT socket option, kernel 4.18+) lets QUIC-style senders pass one large buffer that GSO splits into datagrams.

xdp_md, xdp_buff and safe packet parsing

  

    Why it's examinableBounds-checked parsing is the contract between your program and the verifier; getting it subtly wrong is a verifier-bypass class of bug.
    Interviewer asks"Why can't you read past data_end even though the memory is there? Why check IHL?"
  


  
8.1What your program receives — tap each field

  

  

  

  
Two surprises. First, data and data_end are __u32, not pointers. The verifier rewrites these context accesses into loads from the kernel's internal xdp_buff, producing real pointers of type PTR_TO_PACKET / PTR_TO_PACKET_END. That's why every program starts with (void *)(long)ctx->data. Second, nothing is parsed for you — no skb->protocol, no ip_hdr(). You parse Ethernet, IP and L4 yourself.

Trap — why the IHL check exists
IPv4 headers are 5 to 15 words (20–60 bytes). If you compute ihl * 4 without first rejecting ihl < 5 and re-checking iph + ihl_len against data_end, a crafted packet can push a later pointer past the end in a way that looks checked but was checked against the wrong length. The verifier only knows whether pointer arithmetic is provably bounded — it has no idea what a valid IP header is.

  
Common mistake
Hiding the comparison inside a helper function the verifier can't follow, or comparing against the wrong pointer. The result isn't a runtime crash — the program fails to load. Keep checks inline (__always_inline) and compare the exact pointer you're about to dereference.

  
Caveat — multi-buffer XDP
Since around kernel 5.18 (first mvneta, then i40e, ice, virtio-net and others), an xdp_buff can span several fragments — for jumbo frames, header-split and GRO/TSO-sized redirects. It's opt-in per driver and only used for non-linear frames; at 1500 MTU you're normally in the single-page model. In the kernel the check is xdp_buff_has_frags(); from BPF, a frags-aware program is loaded with SEC("xdp.frags") and uses bpf_xdp_get_buff_len() / bpf_xdp_load_bytes() to reach bytes beyond the first buffer.

9.1DROP vs ABORTED: policy vs exception

  

  
Common mistake
Returning XDP_ABORTED for "this IP is on my blocklist". Under a flood that fires a tracepoint for every single drop and throws away much of the reason you're in XDP. Blocklisted packets are the expected, high-frequency case → XDP_DROP.

  
Trap — "rare" isn't rare for a firewall
A malformed or truncated packet is attacker-reachable: anyone can send garbage on purpose. A flood of short packets that fail the Ethernet/IP bounds check would hit XDP_ABORTED every time, and trace_xdp_exception isn't free. Count it in your flood budget; if garbage floods appear, count malformed packets in a map (or rate-limit the tracepoint) instead of relying on the tracepoint for visibility.


  
9.2XDP_TX — a page flip with two jobs left for you

    2.

    3. 
  

  


  
9.3XDP_REDIRECT — one verdict, three mechanisms

All three targets defer the real transfer to xdp_do_flush() at the end of the NAPI poll. That batching is why redirect-heavy forwarders beat what "one redirect per packet" would suggest.


  
9.4AF_XDP — the zero-copy shortcut

  
Even the normal path's last step, recvmsg(), copies kernel memory into user memory. AF_XDP is a socket type that skips everything: XDP redirects the frame through an XSKMAP into a UMEM — a memory area registered by your process and shared with the kernel. No SKB, no Netfilter, no socket queue, no copy (in zero-copy mode). That's how DPDK-class throughput is reachable with standard kernel eBPF.

  

  
tap a block

  

  

  
Beyond the notes
A UMEM is used through four lock-free rings: FILL (user gives the kernel empty frames), RX (kernel hands filled frames to user), TX (user submits frames to send) and COMPLETION (kernel returns sent frames). "Zero-copy" needs driver support; otherwise AF_XDP falls back to copy mode.

Netfilter, conntrack, the FIB and the socket

  

    Why it's examinableconntrack is the hidden cost behind most "firewall melted under load" incidents; FIB lookups from eBPF are how modern software routers work.
    Interviewer asks"Where do NAT and ESTABLISHED state come from? Why does an empty nftables ruleset still cost CPU?"

11.1PREROUTING and connection tracking

  
After TC, the packet reaches the first Netfilter hook, PREROUTING. Here nf_conntrack looks up the 5-tuple in its hash table: match → existing flow; no match → new entry. That table is where NEW / ESTABLISHED / RELATED / INVALID states come from. Destination NAT also runs here, using the tracked state to rewrite addresses before routing sees the packet.

  
At flood scale the table fills faster than entries expire, and lookups start thrashing the L3 cache. That's why mitigation belongs in XDP: a packet dropped there never creates a conntrack entry.

  
Precision note
"Even an empty nftables ruleset costs you" is true once nf_conntrack is loaded — and it gets loaded by any stateful rule, NAT, or tools like Docker. Traffic can be exempted with a notrack rule in a raw-priority chain.


  
11.2The routing decision (FIB lookup)

  
After PREROUTING the kernel asks the Forwarding Information Base: is this for me, or for someone else? The answer decides which hook fires next — INPUT (local) or FORWARD (then POSTROUTING and out). eBPF can skip the whole chain: bpf_fib_lookup() (from XDP or TC) returns the next hop and egress interface, and with XDP_REDIRECT you get a forwarding plane that never touches Netfilter.

eBPF maps — how programs remember and share state

  

    Why it's examinableMap type is a correctness and performance decision; choosing HASH by default is the most common design smell in eBPF reviews.
    Interviewer asks"How does an eBPF program talk to userspace? Which map type would you use to block a /24?"
  


  
13.1Why maps exist

  
An XDP program sees one packet, returns a verdict and forgets everything. It has no heap, no C-style static globals, and a 512-byte stack. The moment it must remember something between invocations — a blocklist entry, a counter, a rate-limit window — it needs a map. Maps are also the only way in or out: userspace can't call into a running program, and the program can't call out to userspace.


  
13.2A map is a kernel object, not a variable

  
    
    
  • Created by the bpf() syscall (BPF_MAP_CREATE) and referenced by a file descriptor.
    • 
    
  • Every access from your program compiles to a helper call — bpf_map_lookup_elem(), bpf_map_update_elem(), bpf_map_delete_elem() — not a plain memory load.
    • 
    
  • The SEC(".maps") definition is what libbpf finds in your ELF; it creates the maps before your program is verified or attached.
    • 
    
  • max_entries is a hard capacity. For preallocated maps (the HASH default) the kernel reserves memory for all of it at creation.
    • 
  

  


  
13.3Two sides, one piece of memory

  

  
tap a block

  

  
The XDP program looks up on the hot path (every packet). Userspace updates on the control path (an admin adds an IP; a detector promotes a key to "blocked"). Neither waits for the other. And bpf_map_lookup_elem() returns a pointer into the map's memory, not a copy — you must NULL-check it and stay in provable bounds, and two CPUs looking up the same key point at the same bytes (lesson 14).

Common mistake — max_entries in both directions
Too high: memory reserved that you never use. Too low: bpf_map_update_elem() returns -E2BIG in the middle of a flood — exactly when you can't afford a failed insert. Size from the worst case, or use LRU_HASH when eviction is acceptable.

Concurrency, per-CPU maps and pinning

  

    Why it's examinableThe lost-update race passes every functional test and silently weakens a rate limiter under exactly the flood it exists for.
    Interviewer asks"Is entry->packet_count++ safe in XDP? How would you fix it? What happens to a firewall's blocklist when the daemon restarts?"
  


  
14.1Where HASH quietly breaks

  

  
packet_count++ is really read → add one → write. Native XDP runs on the CPU that owns the RX queue, and RSS spreads a large flood from one source IP across several queues — so this increment runs at the same time on several CPUs, on the same key. Both CPUs read 40, both write 41: two packets arrived, the counter moved by one. The limiter undercounts, crosses its threshold late, and lets through packets it should have dropped. A one-packet, one-CPU test looks perfect.

14.2Fix 1 — bpf_spin_lock

  

  
Correct: no lost updates. Cost: every CPU that hits this key now waits in line, which is the very pile-up you spread traffic across queues to avoid.

  
Rules the verifier enforces for bpf_spin_lock
The lock must live inside the map value (the map needs BTF); you may hold only one lock at a time; you can't call other helpers while holding it; and every path must unlock before returning.


  
14.3Fix 2 — PERCPU_HASH

  

  
The XDP-side increment is unchanged and needs no lock: CPU 0 and CPU 2 now update different copies. The cost moves to the read side — userspace sums every CPU's slice, and the total is only as fresh as the last sum.

Map type isn't a global performance dial — it's a per-map decision about what kind of correctness that state needs. For a hard allow/block decision that userspace writes and XDP only reads, plain HASH is correct: there are no concurrent writes to race on.

14.4Pinning — state that survives a restart

  
By default a map lives as long as something holds a reference to it — typically the loader process's fd. Kill the daemon without pinning and the kernel frees the map: every blocklist entry built up over six hours is gone, and the flood you had mitigated comes straight back. Pinning places the map at a path in the bpffs virtual filesystem (/sys/fs/bpf), which holds its own reference.

The verifier — a proof, not a test

  

    Why it's examinableThe verifier is the reason eBPF exists at all; its decidability constraints explain every "annoying" language limitation.
    Interviewer asks"What does the eBPF verifier check, when does it run, and why not just trust root?"
  


  
15.1The mental model

  
The verifier does not run your code. At load time, inside the bpf() syscall, it proves a property about every possible execution: whatever input arrives, this program terminates, touches only memory it's allowed to, and reads only memory that has been initialized. Proving that cheaply requires a language constrained enough that the proof is always decidable. Every limitation you'll hit is downstream of keeping that proof tractable.

  

  
tap a block

  

  
Analogy
A test is a driving examiner watching you drive one route. The verifier is an examiner who reads your route plan and refuses the licence unless they can prove that every possible route, in any weather, ends safely. Strict — but once you pass, nobody rides along (no runtime checks), so you drive at full speed.


  
15.2The four checks

  

    
1 · Termination
Kernel code can't hang: an infinite loop in XDP is a wedged CPU in softirq. Historically backward jumps were banned; since kernel 5.3 bounded loops are allowed if the counter's upper bound is provable.

    
2 · Stack depth
The 512-byte stack limit is proven statically along every call path. A big local array fails at load, not at run time.

    
3 · Uninitialized reads
Stack bytes must be written before they're read or passed to a helper. Stricter than C — and a security control that stops leaking old stack contents to userspace.

    
4 · Memory safety
Every dereference must be provably in bounds and of the right pointer type. This is where most people meet the verifier (lessons 16–17).

  

  

  


  

    
ApproachKernel moduleVerified eBPF program

    
      
Safety guaranteeNone — one bad pointer panics the boxProven at load time

      
SpeedNativeNative (JIT), no runtime checks

      
LanguageFull CRestricted C: bounded loops, 512 B stack, typed pointers

      
Load / replaceinsmod, crash riskLoad and swap at runtime

      
Kernel ABIRebuild per kernelStable helpers; CO-RE via BTF

    


  
Key concept
The verifier is the price you pay once at load so you never pay it on the hot path: no runtime bounds checks, no garbage collector, no sandbox trap.

  
Beyond the notes — how it stays fast
The verifier forks its analysis at every branch, which would explode exponentially. State pruning saves it: if a state reaching an instruction is covered by a state already proven safe there, that path stops. There is still a complexity budget of 1,000,000 processed instructions ("too many instructions" → split the program with tail calls). For loops with large bounds, the bpf_loop() helper (5.17+) is often easier to verify than an open-coded loop.

  
Trap
"It's valid C, so it should load." The verifier rejects programs that could misbehave, even if they never would with your real data. It declines to assume anything it can't prove.

17.6Bytecode decoder — what "(61)" and "(0f)" mean

  
Every eBPF instruction is 8 bytes: opcode (8 bits) · dst_reg (4) · src_reg (4) · off (16, signed) · imm (32, signed), little-endian. The opcode's low 3 bits are the class. For arithmetic/jump classes the rest is source (1 bit: K = constant, X = register) + operation (4 bits); for load/store classes it's size (2 bits) + mode (3 bits).

Quick-reference cheat sheet

  

    
RX path order
NIC (RSS hash) → DMA → RX ring
→ IRQ → NAPI poll (softirq)
→ XDP (native)          ← no SKB
→ build_skb() → GRO
→ RPS/RFS (optional)
→ TC ingress            ← __sk_buff
→ NF PREROUTING (conntrack, DNAT)
→ FIB → INPUT → socket → recvmsg()
      → FORWARD → POSTROUTING → NIC

    
XDP verdicts
XDP_DROP      recycle page, cheapest
XDP_PASS      build_skb → stack
XDP_TX        same NIC; swap MAC, fix csum
XDP_REDIRECT  devmap | cpumap | xskmap
              flushed at end of poll
XDP_ABORTED   drop + tracepoint
              (exceptions, not policy)

    
TC returns
TC_ACT_OK        0  pass
TC_ACT_SHOT      2  drop
TC_ACT_PIPE      3  next action
TC_ACT_REDIRECT  7  redirect
attach: tc qdisc add dev X clsact
        tc filter add dev X ingress \
          bpf da obj p.o sec tc

    
XDP attach modes
xdp          auto: native, else
             SILENT generic
xdpdrv       native or error  ← prod
xdpgeneric   force SKB mode
xdpoffload   NIC only, errors if no HW
check: ip -d link show dev eth0
  xdp/id:N        native
  xdpgeneric/id:N SKB already built

    
ethtool one-liners
-l / -L combined N   queue count
-x                   RSS key + RETA
-g / -G rx N         ring sizes
-k / -K gro on       offloads
-S                   driver counters
-i                   driver name
/proc/interrupts     IRQ per queue
/proc/irq/N/smp_affinity_list

    
RPS / RFS
echo ff > /sys/class/net/eth0/
  queues/rx-0/rps_cpus    # CPUs 0-7
echo 32768 > /proc/sys/net/core/
  rps_sock_flow_entries   # global
echo 4096 > .../rx-0/rps_flow_cnt
  # ≤ global / nqueues
RFS needs RPS. Both run after XDP.

    
Offloads
TSO  TX  NIC cuts TCP        on
GSO  TX  kernel cuts late    on
GRO  RX  NAPI merges flows   on
LRO  RX  NIC merges, lossy   OFF
UFO  removed in 4.14
XDP sees pre-GRO wire frames.
XDP_TX/REDIRECT bypass TSO.
Rewrite bytes → fix checksum.

    
Pick a map
exact key          HASH
never-full flows   LRU_HASH
CIDR prefix        LPM_TRIE (NO_PREALLOC)
dense index        ARRAY
hot counter        PERCPU_HASH/ARRAY
events → user      RINGBUF
jump table         PROG_ARRAY
redirect           DEVMAP/CPUMAP/XSKMAP

Verifier fixes
unbounded access   add if (i >= N) return

                   / bpf_loop()

build with -g, log_level 2, big buffer
grep -v mark_precise
